# Официальный бот компании «Синай»

Один асинхронный Python-сервис для Telegram и MAX: регистрация, проверка принадлежности контакта, сопоставление с существующими карточками amoCRM, ручная проверка, персональные ссылки, календарные рассылки и интерактивный `/admin`. Новые контакты и сделки не создаются: единственная разрешённая запись в CRM — примечание `common` существующей сделки.

В исходном каталоге при разработке находился только `.env`. Существующих исходников и БД не было. Реальные сервисы не запускались, webhook не перенастраивались, сообщения и примечания в CRM не отправлялись.

## Подтверждённые настройки аккаунта

Выполнены только чтения `GET /api/v4/leads/pipelines`, Telegram `getMe` и `getWebhookInfo`. Воронка **8993570** существует и называется **«Успешно завершенные»**. Telegram username — **sinai_news_bot**, webhook на момент проверки отсутствовал. MAX-токен в исходном `.env` пустой; доступ к реальному MAX не проверялся.

Актуальные официальные методы и форматы перечислены в [docs/API.md](docs/API.md). Дата проверки документации: 12.10.2026. MAX использует `https://platform-api2.max.ru`, авторизация токеном в заголовке `Authorization`, HTTPS webhook на 443 и `X-Max-Bot-Api-Secret`. TLS-проверка никогда не отключается.

## Быстрый безопасный запуск

Требуется Python 3.12+. Windows PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements-dev.lock
.\.venv\Scripts\python -m pip install --no-deps -e .
.\.venv\Scripts\python -m pytest -q
.\.venv\Scripts\python -m ruff check sinai tests
.\.venv\Scripts\sinai doctor
.\.venv\Scripts\sinai plan
.\.venv\Scripts\sinai serve
```

Linux:

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r requirements-dev.lock
.venv/bin/pip install --no-deps -e .
.venv/bin/pytest -q
.venv/bin/sinai doctor
.venv/bin/sinai serve
```

Настройки читаются из `.env` (путь можно задать `ENV_PATH`). Начальная `.env` сохранена; добавлены отсутствующие безопасные параметры и случайные секреты webhook. Пример всех параметров — [.env.example](.env.example), он не содержит токенов.

По умолчанию `TEST_MODE=true`, `BROADCASTS_ENABLED=false`, `CRM_NOTES_ENABLED=false`. В тестовом режиме исходящие сообщения имитируются в журнале событий `message_test`, примечания получают состояние `test`, рассылки не создают доставки и не расходуют календарные периоды. `plan` показывает план без отправки. Чтение CRM выполняется реально, если используются реальные ключи. Для сквозной локальной проверки можно POST-ить тестовые webhook с соответствующими секретными заголовками; сервер сам не включает polling и не забирает обновления у другого сервиса.

## Что заполнить для production

| Переменная | Значение |
|---|---|
| `MAX_BOT_TOKEN` | Токен MAX из кабинета MAX для бизнеса |
| `MAX_BOT_USERNAME` | Имя MAX-бота для `https://max.ru/<имя>?start=...` |
| `PUBLIC_BASE_URL` | Публичный HTTPS-адрес сервиса без завершающего `/` |
| `PUBLIC_HOST` | DNS-имя для Caddy, без `https://` |
| `TG_WEBHOOK_SECRET`, `MAX_WEBHOOK_SECRET`, `AMO_WEBHOOK_SECRET` | Случайные независимые секреты; локально уже сгенерированы, перенести на сервер |
| `TG_MANAGER_IDS`, `MAX_MANAGER_IDS` | Раздельные списки ID менеджеров через запятую; пусто = только администраторы |
| `AMOCRM_REFRESH_TOKEN`, `AMOCRM_CLIENT_ID`, `AMOCRM_CLIENT_SECRET`, `AMOCRM_REDIRECT_URI` | Заполнить для обычной OAuth2-интеграции; долгосрочный токен работает без refresh |
| `MAX_CA_BUNDLE` | При необходимости путь к проверенному PEM-сертификату/набору сертификатов Минцифры, доступному внутри контейнера |

`ADMIN_ID=8608404966`, `MAX_ADMIN_ID=185607445` уже настроены. `/admin` доступен только соответствующему ID в личном диалоге, `/link` — ему и явно перечисленным менеджерам.

Обычный OAuth2 access token обновляется при 401 под async-lock: один обмен `/oauth2/access_token`, оба новых токена записываются в `.env` одной атомарной заменой. Каталог `.env` должен быть доступен сервису для записи. Не передавайте токены одновременно через неизменяемые environment variables: они перекроют обновлённый `.env` при следующем запуске. Если обмен OAuth завершился с неизвестным результатом, смотрите ошибки и восстановите токены из настроек интеграции; слепой повтор refresh не выполняется.

## Docker Compose и HTTPS

Для нового выделенного сервиса с незанятыми портами 80/443:

```bash
mkdir -p config data
cp .env config/.env
chmod 700 config data
chmod 600 config/.env
sudo chown -R 10001:10001 config data
```

В `config/.env` заполнить публичный адрес и ключи, установить `TEST_MODE=false`; оставить массовые рассылки и запись примечаний выключенными до проверки регистрации. В корневом `.env` заполнить `PUBLIC_HOST` — он нужен Compose для Caddy. Направить DNS A/AAAA на сервер. Caddy получает доверенный TLS-сертификат автоматически.

Сначала собрать образ и проверить конфигурацию, затем зарегистрировать webhook **до запуска постоянного bot-процесса**:

```bash
docker compose build
docker compose run --rm bot sinai doctor
docker compose run --rm bot sinai setup-webhooks
docker compose up -d
docker compose logs --tail=100 bot
```

`setup-webhooks` — явная команда, которая изменяет webhook только этих ботов, не удаляет pending updates и не меняет webhook amoCRM. До её выполнения убедитесь, что эти токены не обслуживаются другой системой. Для amoCRM через настройки webhook создать подписку на **status_lead** и **update_lead** по адресу `PUBLIC_BASE_URL/webhooks/amo/AMO_WEBHOOK_SECRET` (подставить значение секрета из `.env`). Не отключать существующие CRM-подписки. Подписка amoCRM намеренно не создаётся автоматически.

Если на сервере уже есть reverse proxy и сервисы на 80/443, используйте имеющийся proxy для нового домена и upstream `127.0.0.1:8000`; не запускайте Caddy из Compose поверх существующего. Альтернатива — [ops/sinai.service](ops/sinai.service) с выделенным пользователем `sinai` и отдельными `config/`, `data/`. Доступ снаружи разрешайте только к webhook и health endpoints через HTTPS. Не включайте access logs для секретного CRM-пути.

После проверки реальной регистрации установить `CRM_NOTES_ENABLED=true` и перезапустить. После проверки плана включить `BROADCASTS_ENABLED=true` и перезапустить. Изменение `.env` само по себе не меняет работающий процесс. Ранее имитированные примечания можно отдельно поставить в очередь командой `sinai replay-test-notes` при остановленном сервисе.

## Регистрация и сопоставление

`/start` показывает требуемое приветствие и две inline-кнопки. Telegram получает телефон только через reply-кнопку `request_contact=true`, `contact.user_id` должен равняться отправителю. В MAX используется inline `request_contact`; проверяются HMAC-SHA256 от исходной строки vCard и, если присутствует, `max_info.user_id`. Контакты без корректного `hash` отклоняются. Номер извлекается из vCard парсером, учитываются folded lines; принимается единственный номер.

Российские номера приводятся к `+7...`, пробелы, скобки и добавочные номера удаляются. Международные номера сохраняют код страны. Поиск `GET /api/v4/contacts?query=...` выполняется по вариантам номера, с полной пагинацией; совпадение принимается только после локального сравнения реальных `PHONE`. Уникальный контакт с единственной связанной сделкой может сопоставляться автоматически. При нескольких контактах или сделках — ручная заявка.

Если телефон не найден, бот запрашивает ФИО. Выполняются запросы по перестановкам, отдельным словам, сокращениям и регистру; дополнительно строится локальный индекс всех доступных CRM-контактов для ё/е, пробелов и опечаток. Индекс обновляется по TTL, замена атомарная. Если пагинация превысила `MAX_CONTACT_PAGES`, поиск завершается ошибкой, а частичные результаты не используются для автоопределения. Кандидаты ранжируются локально; сохраняются до 30 наиболее похожих контактов и их сделки. **Любое совпадение только по ФИО требует проверки человека**, включая точное уникальное имя. Низкий score не доказывает отсутствие человека в CRM; администратор может выбрать карточку вручную.

`/link ID_сделки` или `/link https://sinai24.amocrm.ru/leads/detail/ID` возвращает отдельные Telegram/MAX ссылки. Если контактов несколько, менеджер явно указывает `/link ID_сделки ID_контакта`. Случайный 256-битный токен связан с платформой, lead/contact, сроком действия и первым открывшим его аккаунтом. После подтверждения контакта токен погашается. Другой аккаунт или повторное использование не допускаются. Номер должен точно совпасть с целевым CRM-контактом и не иметь конфликтующих совпадений. Ссылку следует передавать только нужному клиенту; открытие ссылки само по себе не подтверждает личность.

При успешном сопоставлении создаётся читаемое примечание и стабильный маркер `[sinai:...]`. Перед POST проверяются все страницы существующих примечаний; повторная регистрация не создаёт новое примечание той же связи. Называния сделок не используются для поиска ФИО. Сохраняются method, actor, PHONE-снимок ручного решения и история событий.

## Сегментация и рассылки

В процессе регистрации и сверки проверяются **все связанные с контактом сделки** через API. Любая сделка в `8993570` назначает `completed`. Перед реальной рассылкой повторно проверяются воронка, телефон/связи и сделки. CRM webhook служит сигналом для повторного API-чтения; присланные pipeline/status не считаются истиной. Стартовая и периодическая сверка охватывают всех зарегистрированных клиентов. Новые связанные сделки также обнаруживаются при сверке контакта.

Возврат из completed в active выполняется только явным решением администратора. Если сделка всё ещё в завершённой воронке, последующая CRM-сверка восстановит completed. Изменение телефона/связи карточки приостанавливает канал и создаёт ручную заявку. Ручное подтверждение несовпадающего телефона действует для записанного PHONE-снимка; последующее изменение CRM требует новой проверки.

Даты в UTC, расчёт календаря и отображение — Asia/Krasnoyarsk. Интервалы active/completed независимы (1 или 2 месяца), меняются в `/admin`. Первая рассылка после соответствующего интервала; каждое следующее число вычисляется от исходной подписки, например 31 января → 28 февраля → 31 марта. Смена сегмента, канала или `/start` после отписки не меняет начальную дату. При присоединении второй платформы клиент сохраняет самую раннюю дату подписки.

На одного CRM-контакта — один клиент, Telegram/MAX — отдельные аккаунты. Предпочитаемый канал по умолчанию Telegram; `/channel` выбирает текущую платформу. Если выбранный канал недоступен, используется другой подтверждённый незаблокированный канал. `/stop` отключает рассылки клиента во всех связанных платформах, `/start` восстанавливает текущий аккаунт. Если блокировка обнаружена как явный 403, канал исключается; возможна безопасная доставка в другой канал. Если MAX возвращает иной код вместо 403, ошибка сохраняется для проверки администратора, без предположения о блокировке.

После простоя планируется только последний наступивший период. Старые задания повторной отправки пропускаются, если наступил следующий период или изменилась актуальная двухмесячная сетка. Пропущенные сообщения не отправляются пачкой. Уникальность `(client_id, cycle)` защищает от повторного планирования даже при смене канала/сегмента/интервала.

## Админ-панель

`/admin`: статистика сегодня / 7 / 30 дней / всё время, подписчики, ручные заявки, история рассылок, ошибки CRM, ближайшие отправки, интервалы и сверка всех клиентов. Списки по 5 записей, кнопки страниц и возврата. Статистика явно разделяет уникальных подтверждённых клиентов, аккаунты и события периода; непроверенные аккаунты не объявляются уникальными клиентами.

В заявке есть прямые ссылки на контакт и сделку, выбор кандидата и отдельное подтверждение. Кнопки связаны с версией списка кандидатов: устаревшее подтверждение отклоняется. Для заявки без кандидатов команда `/match ID_заявки ID_контакта ID_сделки` добавляет проверенную связанную карточку, затем администратор подтверждает кнопкой. Ручное решение требует проверки личности сотрудником; бот не может проверить это вместо него.

В разделе ошибок можно повторить синхронизацию/сверку/примечание. В карточке клиента можно вручную вернуть active. В истории рассылок доставка `unknown` может быть отмечена подтверждённой после проверки в мессенджере. Неподтверждённые доставки не повторяются автоматически.

## Восстановление и эксплуатационные границы

SQLite с WAL, foreign keys, версионируемыми SQL-миграциями и transactional outbox. Входящий webhook подтверждается после сохранения задания; дубли по Telegram update_id, MAX mid/callback_id и CRM payload-hash не создают вторую обработку. Фоновый обработчик один, межпроцессный file-lock не допускает второй экземпляр с той же БД. **Запускать только один Uvicorn worker, без `--reload`.** Для горизонтального масштабирования потребуется адаптация очереди/транзакций под PostgreSQL; текущий вариант предназначен для одного выделенного процесса и локального диска, не сетевого FS.

Отписка `/stop` применяется уже при приёме проверенного webhook, до обработки очереди, чтобы длинный поиск CRM не задерживал отключение рассылок. Сообщение, уже принятое API мессенджера, отозвать таким способом нельзя. При ручной замене основной сделки устаревшая связь сохраняется в аудите, а текущая привязка заменяется.

GET-запросы повторяются с backoff и jitter при транспортных ошибках/5xx; 429 учитывает retry_after. Очередь сохраняет attempts, next run, last_error и историю ошибок. До 10 попыток, после этого задача остаётся в failed для ручного запуска. Скорость amoCRM ограничена примерно 3 запросами/с, Telegram — менее 1 сообщения/с, MAX — менее 2 сообщений/с. Обычные исходящие сообщения и broadcasts не повторяют POST после неопределённого результата.

API Telegram/MAX не предоставляют ключ идемпотентности для отправки сообщения. Поэтому гарантировать одновременно отсутствие потерь и строго exactly-once через сетевой сбой невозможно. После timeout, 5xx или завершения процесса в середине отправки результат **unknown**: слепой повтор запрещён. Это осознанное предпочтение защиты от дублей. Для CRM-примечания с неизвестным результатом выполняется поиск маркера; если его нет, повторное создание блокируется до ручной проверки. Если примечание точно не было создано, оператор при остановленном процессе может явно вернуть его из unknown в pending; это решение требует проверки карточки и фиксирования причины во внешнем журнале эксплуатации. Обычный повтор задания не сбрасывает защиту unknown.

`/health/live` проверяет HTTP-процесс; `/health/ready` — БД и работающий обработчик. Наличие ошибок доступа к API отражается в админ-панели, readiness не означает доступность всех внешних API. Подключите мониторинг HTTPS, failed/unknown jobs и свежести `clients.last_crm_check`; длинный полный поиск ФИО может задержать остальные задачи одного обработчика. Доступ к БД/backup/.env ограничивать пользователем сервиса; payload содержит персональные данные. HTTP-клиенты и proxy не пишут в логи токены/секретные URL.

Резервная копия через SQLite backup API, в том числе при работающем сервисе:

```bash
.venv/bin/sinai backup --output backups/sinai.sqlite3
```

Восстановление: остановить bot, проверить backup в отдельном каталоге, заменить **только** `data/sinai.sqlite3` этого проекта и убрать его старые WAL/SHM при остановленном процессе, запустить сервис. Нельзя копировать обычным `cp` только main-файл работающей WAL-базы. Регулярно проверяйте восстановление резервной копии. Команды `doctor`, `setup-webhooks`, `reconcile`, `plan`, `prune`, `replay-test-notes` используют тот же process-lock и требуют остановить постоянный bot; backup — исключение.

`sinai prune` удаляет payload завершённых входящих событий/ответов старше 30 дней, сохраняя ключи дедупликации, аудит и историю доставок. Периодическую очистку запускать в окне обслуживания. Функции удаления CRM-карточек, изменения существующих систем и миграции сторонних баз отсутствуют.

## Проверки

Автотесты используют отдельные временные БД и fake/mocked API, не отправляют реальные сообщения и не меняют CRM. Покрываются нормализация PHONE, ложные результаты query, пагинация, fuzzy-ФИО, неоднозначность контактов/сделок, TG чужой контакт, MAX HMAC, одноразовые/истёкшие ссылки, ручное решение и его версия, уникальные клиенты, сегментация, календарные месяцы/високосный год/часовой пояс, оба интервала, один канал, отписка/возобновление, блокировка, 429, неопределённый результат, восстановление очереди, OAuth refresh и защита от создания карточек.

Реальный сквозной запуск MAX, TLS домена, webhook-доставка и OAuth refresh вашей интеграции должны быть проверены после заполнения отсутствующих параметров. До этого проект не считается развернутым production-сервисом.
