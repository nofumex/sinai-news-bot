# Синай · Telegram/MAX · amoCRM

Обновление существующего [sinai-news-bot](https://github.com/nofumex/sinai-news-bot) до механики v2. Сохранены модули platforms/CRM/DB/worker/scheduler/admin, SQLite WAL, OAuth2, история, миграции 001/002, календарные ежемесячные рассылки и общие active/completed. Добавлена **003_polling_registration_campaigns**: существующие ID клиентов, аккаунтов, примечания и доставки сохраняются. База не пересоздаётся при обновлении.

**Поиск по ФИО и обязательное ручное подтверждение удалены. Только polling; HTTP-сервер, Caddy, публичные порты и домен не нужны.**

## Регистрация

`https://t.me/sinai_news_bot?start=32376521` или `https://max.ru/<MAX_BOT_USERNAME>?start=32376521` проверяет реальную сделку через `GET /api/v4/leads/{id}?with=contacts`. Первая успешная транзакция резервирует lead_id в `lead_claims`, где lead_id — первичный ключ, subscription_id — UNIQUE. Резервация общая для обеих платформ, сохраняется после рестарта и не освобождается при /stop. Один аккаунт не может автоматически резервировать несколько сделок.

Бот показывает приветствие и кнопки «Я действующий клиент» / «Моя процедура уже завершена». После выбора подписка завершена, контакты и ФИО не запрашиваются. CRM имеет приоритет над выбором. Создаётся `common`-примечание существующей сделки с платформой, user_id, датой, сегментом и методом. Записи контактов/сделок создавать/изменять запрещает allowlist CRM-клиента.

Числовой lead_id **не подтверждает личность**. Метод `numeric_unverified`, identity_verified=0; имя, телефон и содержимое CRM-карточки клиенту не показываются. Для отсутствующей/занятой/невалидной ссылки одинаковый ответ без персональных данных. Лимиты: по умолчанию 5 новых проверок аккаунту и 100 всем аккаунтам за час, сохраняются в SQLite. Нормальный повтор той же уже занятой своим аккаунтом ссылки не расходует лимит и не добавляет примечание. `/link ID_сделки` доступен администраторам и указанным менеджерам, возвращает числовые ссылки без ФИО.

Без start-параметра подписка начинает действовать после выбора группы. Контакт необязателен, есть «Пропустить». Для Telegram проверяется contact.user_id; для MAX — HMAC-SHA256 от исходного vcf_info и max_info.user_id, если он есть. Поиск исключительно по нормализованному PHONE: результаты `contacts?query=...` проверяются локально по полям PHONE, затем читаются связанные сделки. Единственная точная пара контакт/сделка привязывается автоматически. Нет совпадения, несколько контактов/сделок, конфликт занятой неподтверждённой карточки — пользователь остаётся подписанным без CRM. Нет заявок на обязательное подтверждение, запросов ФИО или fuzzy-поиска.

Периодическая сверка повторяет телефонный поиск для ещё не подтверждённых аккаунтов, когда появляются новые данные. Без предоставленного телефона автоматический поиск невозможен; администратор может указать lead_id в `/admin → Несинхронизированные → аккаунт → Привязать`. Ввод lead_id уже является решением администратора, дополнительное обязательное подтверждение не используется. Если выбранная сделка занята незавершённой регистрацией, это явное решение администратора может перенести резервацию с аудитом. Если уже есть зарегистрированный получатель той же сделки, аккаунты объединяются для защиты от дублей. Личность после такой административной привязки остаётся неподтверждённой.

Повторная автоматическая числовая регистрация другого аккаунта на занятый lead_id запрещена. Точное совпадение телефона с **уже подтверждённым** CRM-контактом может присоединить вторую платформу к существующему клиенту; это не создаёт новую резервацию сделки. Похожие имена или совпадение только lead_id никогда не доказывают, что это один человек.

## Сегменты и регулярные рассылки

Воронка `8993570`, фактическое название «Успешно завершенные», проверяется через API. Привязанный клиент получает completed при наличии сделки в этой воронке; для подтверждённого контактного клиента проверяются также все сделки контакта. Свежая CRM-проверка имеет приоритет над начальным выбором. Подтверждённое чтением CRM перемещение обратно в другую воронку может вернуть active — это фиксируется в аудите. Несинхронизированные получают рассылки выбранной группы даже при недоступности CRM.

Интервалы active/completed независимо 1 или 2 месяца, настраиваются в `/admin`. Первый период после даты подписки, последующие рассчитываются от неё по календарным месяцам в Asia/Krasnoyarsk: 31 января → последний день февраля → 31 марта. Простой не создаёт пачку пропущенных сообщений. Смена сегмента/платформы, привязка и объединение не сбрасывают дату; объединённый клиент сохраняет наиболее раннюю дату. Проверяются история всех объединённых ID и время прошлой отправки, чтобы изменение якоря не создало дополнительную рассылку.

Предпочитаемый канал — PREFERRED_PLATFORM, по умолчанию Telegram. `/channel` выбирает текущую платформу; второй канал используется, если предпочитаемый недоступен. `/stop` действует на весь объединённый клиентский профиль; /start возобновляет текущий аккаунт, сохраняя дату. При polling отписка применяется при сохранении обновления, до работы CRM-очереди. Уже отправляемое через API сообщение отменить нельзя.

## Произвольная рассылка /message

Доступ только ADMIN_ID в Telegram и MAX_ADMIN_ID в MAX, в личном диалоге. Выбор active/completed/все → отправка исходного сообщения с нужным форматированием/медиа → предпросмотр → «Отправить», «Изменить», «Добавить часть», «Отмена». Альбом собирается из нескольких polling-событий. Можно составить кампанию из нескольких сообщений; каждая часть имеет отдельную запись состояния доставки.

Предпросмотр отправляется администраторам **каждой используемой платформы**. Кнопка отправки появляется только после успешной доставки всех предпросмотров. Сохраняются revision, факт тестового/production-предпросмотра и снимок аудитории. Изменение контента, получателей или предпочитаемого канала требует нового предпросмотра. Тестовый предпросмотр не разрешает последующий production-запуск. При TEST_MODE=true исходящие предпросмотры имитируются, рассылка клиентам не запускается.

В Telegram нативные сообщения копируются `copyMessage`, альбомы — `copyMessages`, сохраняя форматирование, подписи и файлы. В MAX используется документированный forward link на исходное сообщение; сохраняются поддерживаемые платформой вложения и нативное оформление, **MAX может показывать информацию о пересылке**. Нативный источник фиксируется на сообщении предпросмотра бота, чтобы редактирование исходного сообщения администратора не меняло уже подтверждённую кампанию.

Между платформами жирный/курсив/подчёркивание/зачёркивание/code/ссылки/цитаты переводятся в HTML, медиа скачиваются ограниченным потоком и заранее загружаются в MAX через `/uploads`; Telegram принимает подготовленные файлы multipart. MAX attachment.not.ready повторяется с задержкой без повторного создания сообщения. Токены медиа и варианты сохраняются в БД. Видео/фото/файлы/аудио обрабатываются в рамках API-лимитов. Непереносимые вложения (например, нативные стикеры/опросы), неподдерживаемые комбинации или слишком длинные подписи **блокируют предпросмотр**, а не молча теряют данные. Для одной части кампании можно добавить отдельный нативный вариант Telegram/MAX из соответствующего `/admin → Кампании → номер → Вариант ...`. Это сохраняет платформенные особенности. Для нескольких частей используйте совместимые исходные сообщения либо отдельные кампании.

Снимок получателей создаётся одной транзакцией запуска. Очередь, ограничения скорости, повторы явно отклонённых запросов, progress и история в `/admin → Кампании`. Единица счёта — получатель, не отдельная часть. Отдельно видны ожидание, успех, ошибки, отписки, skipped/duplicate и unknown. После объединения аккаунтов ещё не отправленные дубли кампании пропускаются. Повторная кнопка отправки и перезапуск не создают вторую кампанию/вторую доставку. Уже отправленные части не повторяются после 429 или сбоя между частями. После блокировки канал не используется в следующих кампаниях; текущая многосоставная кампания не переключается посреди доставки на другую платформу, чтобы не раздвоить сообщение.

## Безопасный запуск и настройки

Python 3.12+. Секреты только в `.env`, в репозитории — [.env.example](.env.example). Текущие безопасные настройки сохранены: `TEST_MODE=true`, `BROADCASTS_ENABLED=false`, `POLLING_ENABLED=false`, `CRM_NOTES_ENABLED=false`.

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements-dev.lock
.\.venv\Scripts\python -m pip install --no-deps -e .
.\.venv\Scripts\python -m pytest -q
.\.venv\Scripts\python -m ruff check sinai tests
.\.venv\Scripts\sinai backup --output backups/before-v2.sqlite3
.\.venv\Scripts\sinai migrate
.\.venv\Scripts\sinai plan
```

Linux: аналогичные команды `.venv/bin/python`, `.venv/bin/sinai`. Миграция автоматически применяется при запуске; заранее сделайте backup. Миграция перестраивает только таблицу clients для nullable contact_id, в одной транзакции, с сохранением IDs и проверкой foreign_key_check до commit. Миграции 001/002 не изменены. Исторические reviews/links сохраняются, старые name-search jobs отзываются, персональный индекс для поиска ФИО очищается. Старые подписанные несопоставленные аккаунты становятся локальными получателями выбранной группы.

Заполнить:

| Параметр | Для чего |
|---|---|
| TG_BOT_TOKEN / TG_BOT_USERNAME | Telegram токен и username |
| MAX_BOT_TOKEN / MAX_BOT_USERNAME | MAX токен и имя для числовых ссылок |
| ADMIN_ID / MAX_ADMIN_ID | Администраторы соответствующих платформ |
| TG_MANAGER_IDS / MAX_MANAGER_IDS | Необязательный whitelist для /link |
| AMOCRM_BASE_URL / AMOCRM_ACCESS_TOKEN | Существующий аккаунт и токен |
| AMOCRM_REFRESH_TOKEN / CLIENT_ID / CLIENT_SECRET / REDIRECT_URI (с префиксом AMOCRM_) | Только для обычной OAuth2-интеграции; долгосрочный access token refresh не требует |
| MAX_CA_BUNDLE | При необходимости доверенный PEM Минцифры, добавляется к системному trust store |
| POLLING_ENABLED | true для реального приёма событий; TEST_MODE всё ещё блокирует исходящие сообщения |
| POLL_TIMEOUT / MAX_POLL_MIN_SECONDS | 25 секунд / минимум 2 секунды между MAX-запросами; timeout MAX не превышает 90 секунд |
| RECONCILIATION_SECONDS | Период чтения карточек и повторного phone matching, по умолчанию час |
| LEAD_START_LIMIT / GLOBAL_LIMIT / WINDOW_SECONDS (с префиксом LEAD_START_) | Защита от перебора, 5 / 100 / 3600 по умолчанию |
| MEDIA_MAX_BYTES | По умолчанию 20 МБ для межплатформенного переноса |

OAuth2 refresh выполняется под lock; оба обновлённых токена атомарно записываются в `.env`. Каталог `.env` доступен сервису для записи. Не дублируйте токены через неизменяемые process environment variables поверх файла. При неопределённом результате обмена токенов потребуется восстановить OAuth credentials. TLS-проверка никогда не отключается.

## Polling на VPS

Остановить старый экземпляр именно этого бота, сохранить backup, установить зависимости/обновить файлы и выполнить `sinai migrate`. Перед реальным polling выполнить **явно** `sinai setup-polling`: команда удаляет Telegram webhook без сброса pending updates и MAX webhook-подписки этого bot token. Чужие токены и существующие webhook amoCRM не меняются. Runtime при обнаружении активного webhook откажется запускать polling и не будет сам перенастраивать сервисы. Не оставляйте второй старый polling-процесс на другом сервере: общий file-lock защищает только экземпляры с одной БД; Telegram 409 также выявляет конфликт.

Установить `POLLING_ENABLED=true`, оставить TEST_MODE и запрет рассылок, запустить `sinai serve`. Входящие события уже сохраняются в реальную БД, исходящие сообщения имитируются. Для проверки живого диалога затем явно установить `TEST_MODE=false`, оставив `BROADCASTS_ENABLED=false` и `CRM_NOTES_ENABLED=false`. После проверки регистрации/предпросмотров/плана включать необходимые production-флаги и перезапускать процесс. До этого никакой реальной клиентской рассылки нет. Тестовые примечания можно отдельно поставить в очередь `sinai replay-test-notes` при разрешённой записи и остановленном сервисе.

У Telegram offset и MAX marker записываются **в одной транзакции со всей полученной пачкой**. Сначала событие сохранено, потом обновлён курсор. Повторная доставка дедуплицируется. Отдельные HTTP-клиенты polling не блокируют отправку/ответы долгим ожиданием. Reconnect/backoff/jitter, ограничения скорости и сохранение ошибок. Начальный MAX-запрос без marker по официальной документации возвращает только последнее обновление: историю до первого запуска восстановить таким способом нельзя. Не сбрасывайте сохранённый marker вручную.

**MAX официально не рекомендует Long Polling для production** и ограничивает скорость/срок хранения событий без указания численных гарантий на странице `/updates`. Проект использует запрошенный polling, консервативный интервал и сохранение marker, но не обещает восстановить события после простоя дольше серверного хранения. Это ограничение сервиса, а не устранённая программой проблема. [Официальная документация](https://dev.max.ru/docs-api/methods/GET/updates).

Развёртывание Docker:

```bash
mkdir -p config data
cp .env config/.env
chmod 700 config data
chmod 600 config/.env
sudo chown -R 10001:10001 config data
docker compose build
docker compose run --rm bot sinai migrate
docker compose run --rm bot sinai setup-polling
docker compose up -d
docker compose logs --tail=100 bot
```

Нет publish/expose портов, Caddy и public host. `.env` монтируется через writable каталог для атомарного refresh. Альтернатива — [ops/sinai.service](ops/sinai.service), отдельный пользователь, те же config/data. Compose проверяет `sinai health` по heartbeat worker. `sinai status` и `sinai backup` доступны при работающем процессе через readonly SQLite; остальные команды требуют остановить runtime и используют его process-lock. Ошибки провайдеров / свежесть polling видны в status и /admin; health не гарантирует доступность внешних API.

## Надёжность и ограничения

SQLite WAL / FK / миграции / устойчивые jobs; один worker и по одному poller на платформу. Второй процесс с той же БД отказывается запускаться. GET повторяются при transport/5xx; 429 учитывает retry_after. Очередь делает до 10 попыток, затем сохраняет failed для проверки. amoCRM ~3 RPS, Telegram менее 1 RPS отправки, MAX менее 2 RPS отправки; платный Telegram broadcast не используется.

Telegram/MAX не имеют универсального идемпотентного ключа отправки: timeout/5xx или завершение процесса в середине POST дают **unknown**, слепой повтор запрещён. Клиентскую доставку unknown следует проверить вручную по истории; новая кампания не является безопасным способом повторить неизвестную отправку. CRM-примечания проверяют стабильный маркер перед POST; при неизвестном исходе проверяется CRM, отсутствие маркера не даёт автоматического разрешения повторить POST. Exactly-once без риска потери или дубля при сетевом сбое недостижимо на этих API.

Числовые ссылки можно угадать и занять чужую карточку; rate limits и отсутствие выдачи персональных данных уменьшают риск, но не подтверждают личность. Локальные неподтверждённые аккаунты на разных платформах нельзя безопасно объединить без дополнительного основания. Историю сообщений, отправленных до появления такого основания, отменить нельзя; будущие кампании и месячные доставки учитывают объединение.

Перенос медиа ограничен размером, доступностью download URL и возможностями обеих платформ. Native Telegram копия обходит скачивание getFile; межплатформенное скачивание стандартным Telegram API ограничено 20 МБ. Нельзя обеспечить пиксельно одинаковый рендер Telegram/MAX: точный пользовательский контент показывается в обоих нативных предпросмотрах, несовместимость требует отдельного варианта. MAX передаёт файлы/видео не всегда с прямым download URL; в таком случае нужен нативный вариант в Telegram. Доступность оригинала для первого предпросмотра требуется; после него используются закреплённые bot preview сообщения/подготовленные файлы.

БД/media/backup содержат персональные данные и вложения: ограничить доступ пользователем сервиса, делать резервные копии через SQLite backup API. Восстановление — только при остановленном runtime, заменить только собственный data/sinai.sqlite3 и удалить его старые WAL/SHM перед запуском. `sinai prune` удаляет старые payload завершённых входящих сообщений/ответов, сохраняет ключи дедупликации и аудит. Payload кампаний и media не очищаются автоматически, чтобы не сломать историю и восстановление.

## Проверки

Автотесты используют временные БД и mocked API без реальных клиентов: миграция существующих IDs/FK/истории, гонка lead_id между платформами и двумя соединениями, повторные переходы, обход контактного шага, точный/неоднозначный PHONE, появление CRM данных, несовпадающий телефон, две платформы, объединение, приоритет сегментов, календарь, /stop, polling offset/marker и rollback пачки, runtime lock, кампании/предпросмотр/версии/аудитория/части/медиа/429/unknown/перезапуск. Официальные API источники — [docs/API.md](docs/API.md).

Реальный MAX, новые медиа-форматы и Docker-образ необходимо проверить после заполнения MAX credentials и запуска Docker Engine. Код не развёрнут автоматически, никаких реальных клиентских сообщений в ходе разработки не отправлено.
